Advice a person can act on

NØMAÐ compares what each job asked for with what it used, and tells the person what to change, in words a first-year student can follow.

What it saw, in numbers they can check
Which jobs, on which partition, what they asked for and what most of them used.
The line to change
The #SBATCH value to ask for instead, not a lecture about efficiency.
Why, in one sentence
Cores held but unused make other people's jobs wait. Asking for far more time is mentioned only when it made the person wait.
Weekly at most, and easy to stop
An email goes only when there is something new. People turn it off from the Console; accounts that exist only for a course are left out.

What it keeps an eye on

Each collector can be turned on or off per machine, and its thresholds live in nomad.toml, so another center can set its own.

Jobs and queues

Slurm jobs and waits, counted from when a job could start, with a job array counted once. Jobs that fail at start and jobs running past their limit. Guests on a lab's condo are told when the owners need the nodes back, and whether their job will survive a requeue.

Nodes and hardware

CPU, memory and GPUs (real utilisation from DCGM), temperatures, power supplies, fans, and how fast each CPU really runs when busy. Draining and resuming a node from the Console, always as a dry run first.

Interactive servers and login nodes

RStudio and Jupyter sessions left idle or holding the most memory, with actions such as restarting a person's session. Heavy work on a login node is told to the person, with the better way.

Lab workstations and storage

Departmental workstations, read over ssh from one machine. Who holds what on each storage server, and data left unchanged for a year, with a ready-made note to its owner that staff can send.

Work from the browser

Submit a job sized from past runs, see where it would start soonest, run it again or start from a template. Move files between a person's own computer and the clusters, and copy folders between machines, with nothing to install. The Console does it all as the person, through nomad-gate.

Labs, courses and reports

PIs confirm who is in their lab and request accounts from the Console. Term reports for each lab, monthly condo reports for owners, and a usage report for administrators.

Policy watch

Tunnels, proxies, miners, GPUs served to the network, AI agents driving a cluster, and job patterns such as bursts and fail-fast loops. It reads and reports; it never stops anything.

Software licenses

When each license ends, a reminder before it does, and a small test of whether each licensed program still runs on each machine.

Itself

Sites that stop reporting, maintenance windows declared ahead, and the size and growth of its own databases. nomad metrics serve publishes each site's latest readings for Prometheus, and a Grafana dashboard comes with it.

Honest about what it knows

It says when it doesn't know

Pages say what period their numbers cover and how old the latest reading is. A site that goes quiet raises an alert, and something nobody measures is listed as not monitored, never shown in green.

It speaks plainly

"Running out of memory, moving data to and from disk", not "thrashing". Advice names the jobs it is about and the value to ask for.

It never runs as root

Collectors run as ordinary accounts. When the Console acts on a cluster, it acts as the person who asked, with that person's own permissions there.

It shows people what is theirs to see

A student sees their own work, a PI their lab, an instructor their class, staff everyone. Who was shown advice is counted for staff, never named.

It travels light

Python, SQLite and a TOML file. No message queue or time-series database to run.

How it fits together

A small center can run all three parts on one machine; a larger one spreads them out.

{{ partial "architecture.html" . }}

  1. Collect

    On each site, such as a cluster's head node, an interactive server, or a machine that reaches the lab workstations, nomad collect writes what it reads to the site's own SQLite database.

  2. Sync

    The hub runs nomad sync on a timer: it copies each site's database safely, merges them, and records which sites answered, which came from cache and which went quiet.

  3. Serve

    The Console, the emails and the reports read the hub's combined database. nomad metrics serve answers Prometheus.

Get started

NØMAÐ needs Python 3.10 or later. Slurm, sysstat and NVIDIA's tools are used where they are installed.

Try it with made-up data

A synthetic cluster with jobs, nodes, alerts and storage, on your own computer.

pip install nomad-hpc
nomad demo

For the Console, nomad demo --console ~/nomad-demo makes a demo with six people to sign in as: a student, a research assistant, a PI, an instructor, an operator and an admin.

Set it up on your systems

The setup wizard detects the tools on the machine and asks about the rest.

nomad init
nomad collect
nomad sync

Run nomad init and nomad collect on each site, and nomad sync on the hub. The installation guide covers timers, accounts and the hub.

The Console

A FastAPI and React web application that reads the hub's database. It is free software under AGPL-3.0, like the rest of NØMAÐ.

It listens only on its own machine. People reach it through your web server, or through an SSH tunnel that nomad console launch opens for them.
